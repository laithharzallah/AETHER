# AETHER application and database audit — phase 1

Baseline: `6ab87fad3a0a6f278b2c560a1016d48a11e15e29` on `main`.
Database: connected project `zlfwuhwcwmdtyvmuxdxp`, PostgreSQL 17.
This is a source/configuration audit with targeted tests, not a penetration-test certification or a production sign-off.

## Decision

**Not ready for enterprise production. Provisional baseline: approximately 5/10.**
The code is a substantial working foundation, including embedded AI workflows; the most important gaps are authorization, assurance integrity, reproducible deployment, and operational verification.
Scores below are engineering maturity judgments, not measured percentages or an average of passed tests. Unknown operational controls receive no assurance credit.

| Area | Baseline /10 | Evidence and limitation |
|---|---:|---|
| Architecture | 7 | Next.js App Router, server-rendered pages, client workbenches, Server Actions, ten AI routes, typed Supabase access. |
| Authentication/authorization | 3 | Verified `getUser()` checks in AI routes and context helpers, but self-editable profile role; public signup auto-confirms email; many mutations lack role checks. |
| Tenant isolation | 5 | 47/47 public tables have RLS; 10/10 public views use security-invoker. Broad adversarial isolation tests absent; cross-tenant relationship integrity not enforced by single-column FKs alone. |

The branch migrates the deprecated Next 16 middleware convention to `proxy.ts`, preserves rotated cookies on redirects, and returns JSON 401 on API session failures.
- `lib/supabase/admin.ts` is imported by `lib/actions/auth.ts` only. Signup creates Auth user, organization and owner profile in separate privileged operations, with best-effort cleanup. Other application data paths inspected use user-scoped clients and RLS.
- No application realtime subscriptions or arbitrary server-side URL retrieval found in the source search. No Edge Functions deployed. Do not equate this with no backend.

## Tenant boundary assessment

Tenant IDs for ordinary inserts are generally derived from authenticated profile context (`getCtx`, policy/evidence creation, assistant conversation creation), rather than accepted as authorization from client input. Existing-ID reads and updates frequently rely on RLS. That is valid only if RLS, views, RPCs and object relationships are correct; a missing explicit tenant filter is not by itself proof of a leak.

| Domain | Evidence | Outstanding tests |
|---|---|---|
| Users/configuration | Profile/organization RLS; protected profile role/membership; targeted two-tenant profile tests pass. | Role-management lifecycle, invitations, revocation, session expiry, configuration and module entitlements. |
| ERM | Tenant policies, invoker views/RPCs, server-derived org. | Risks, assessments, treatment, KRI, history, polymorphic links and forged related IDs across tenants. |
| Compliance/controls | Programs tenant-scoped; implementations derive tenant via program. Shared regulatory catalog intentionally readable to authenticated users. | Program creation RPC; owner/workspace IDs; mapping consistency; report endpoints. |
| Evidence | Private storage; organization-folder policy; record/link RLS. | Signed URL lifecycle, object replacement/deletion, direct review-field forgery, links to foreign implementations and metadata/object mismatch. |
| Internal audit | Tenant policies, invoker summaries and plan/template RPCs. | Engagements, procedures, workpapers, observations/actions, related evidence/control IDs and approval rules. |
| ICFR | Tenant policies and invoker template import. | Process/control/risk/test/deficiency relationships and owner IDs; direct writes versus UI validation. |
| Briefs/reports/assistant | Briefs tenant-restricted; conversation/message tenant policies; reports read user-scoped data. | Cross-tenant IDs in every report route, conversation history, forged message roles/citations and incomplete-data handling. |

All ten live application views use `security_invoker=true`. All inspected application RPCs remain executable by authenticated users after earlier hardening and run as invoker; anonymous execution is revoked. This supports compatibility but does not replace functional tests of each RPC. `rls_auto_enable` is not executable by anon/authenticated. The private helper definitions use empty search paths and public wrappers remain invokers.

## Target intelligence architecture

Keep Next.js as the authenticated application/BFF. Add a worker boundary for durable ingestion and scheduled jobs, rather than putting long-running retrieval into a page request. A Supabase Edge Function may be appropriate for short jobs; sustained extraction may need a separate worker. Choose based on runtime limits and job requirements.

1. **Official source registry:** regulator, jurisdiction, language, approved domains, source type, retrieval schedule and accountable curator. Start with one Saudi or UAE regulator and a clearly licensed/accessible publication.
2. **Retrieval:** allowlisted HTTPS destinations, SSRF protections across DNS/redirects, size/time/content-type limits, raw snapshot, SHA-256, retrieval timestamp, canonical URL and HTTP metadata. Never treat retrieved text as instructions.
3. **Extraction/normalization:** retain original Arabic/English material, exact page/clause/paragraph locators, effective/publication dates, parser version and normalized obligation versions. Distinguish official clause numbering from thematic mappings.
4. **Change/classification:** compare versioned obligations, classify with versioned prompts/models, cite exact evidence spans, record confidence and unresolved ambiguity; deduplicate with idempotency keys.
5. **Human review:** immutable review events keyed to exact source/extraction versions; reject, request changes, approve or supersede. AI cannot verify its own extraction.
6. **Organization impact:** separate tenant-scoped applicability and mappings to controls, risks, evidence and audit universe; assess gaps only against that tenant's approved context.
7. **Actionable brief:** explain what changed, source/version/effective date, why applicable, impacted controls, next action, owner and due date. Preserve source/reviewer references and uncertainty. Human approval before publication or outbound notifications.

Every AI run should have tenant/user, use case, input evidence versions/hashes, model and prompt version, bounded tool permissions, reserved/actual cost, status, request ID, output schema version, validated citations and review decision. Store source-derived content separately from instructions. Persist only necessary tenant data with retention controls; provider processing locations/terms require a documented deployment decision, not an assumption of GCC compliance.

## Phase 2: tenant relationships and evidence reviews

The baseline scores above remain the pre-remediation assessment. This continuation addresses TENANT-01's direct foreign-key scope and AUTH-02's evidence-specific review boundary; other domains' approval rules and indirect/polymorphic relationships still need testing.

- Reproduced both issues with synthetic users in a rollback-only transaction: a viewer inserted accepted evidence, and inserted an ICFR control referencing a foreign tenant's process. This proved unauthorized writes, not a cross-tenant data-read exploit.
- A read-only mismatch audit across 60 direct tenant-to-tenant foreign keys found zero existing mismatches.
- Added and validated organization-consistent composite constraints for all 60 relationships, backed by 15 parent identity indexes and 60 covering child indexes. Existing indexes were retained. Final constraints retain the original names used by Supabase query hints and preserve original CASCADE / column-specific SET NULL behavior. No production data was rewritten or deleted.
- A compatibility follow-up replaces the initial duplicate single/composite relationships with one composite FK under each original name, avoiding ambiguous PostgREST embedding. Schema cache reload requested. Generated TypeScript types refreshed from live Supabase. Optional RPC arguments now omit absent values; live definitions confirm they default to SQL NULL, preserving semantics.
- `supabase/tests/tenant_relationships.sql` passes after the compatibility change: same-tenant creation; rejected foreign process insertion/reassignment and owner reassignment (including service role); foreign process read/update denial; original SET NULL and CASCADE behavior; 60 validated composite constraints.
- `private.enforce_evidence_review` is SECURITY INVOKER, with empty search path and no public/anon/authenticated direct execution. It rejects pre-approved inserts and non-admin reviews, protects identity/attribution, stamps real reviewer/time, and invalidates approval on metadata/content edits. Privileged provisioning retains its capabilities. The application review action now checks that a row was actually updated.
- `supabase/tests/evidence_review.sql` passes: viewer pre-approval/review rejection, foreign-owner denial, authorized review with canonical attribution/time, approval invalidation and rejection of combined content-edit/approval. Storage bytes can still be changed through storage APIs; immutable object versions/scanning remain FILE-01 work. An append-only review history and separation of duties remain release gates.
- Performance Advisor after indexing reports unused indexes only; no unindexed foreign keys. Security Advisor retains the two previous extension/password notices. No unused indexes were removed.
- Live migration identities: `20260905124419` tenant constraints, `20260905124656` covering indexes, `20260905124800` evidence review, `20260905125026` PostgREST relationship compatibility. Repository filenames match those identities.
- Rollback SQL under `supabase/rollback/` is for explicit incident use, not automatic migration replay. The tenant rollback restores the original FK definitions and drops only the new supporting indexes; it reopens the cross-tenant attachment risk. Neither rollback was executed.

## Phase 1 change verification and rollback

- Profile migration applied live at `20260905025927`; repository filename matches live migration identity. Its assertions verify protected and preserved privileges.

- Application tests: eight groups pass (four URL tests; four proxy/session-cookie, denial and health tests with mocked Auth and real Next request/response objects). Added CI runs lint/typecheck/unit tests/audit/build with non-production placeholders; no credentials embedded.

- Final production build passes on Node 24.19.0 / Next.js 16.3.4 with placeholder credentials. Migrating to proxy removed the Edge-runtime warnings observed in the initial upgraded build. Real production environment values, Node 20 hosting and authenticated workflows were not exercised.
